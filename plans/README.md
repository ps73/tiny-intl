## Corrections from execution

1. **There is no pre-existing `TS2345` in `Translate.tsx`.** Plans 001 and 003
   both claimed the destructured `TranslateProps` union would fail `strict`
   typechecking. Measured: `tsc --noEmit` exits 0 for both adapters, with
   `src/Translate.tsx` confirmed in the compilation. TypeScript *does*
   discriminate this union, because every member gives `count`/`date`/`number` a
   unit type (`number` vs `undefined`) — the shape TS 4.6+ control-flow analysis
   for destructured discriminated unions handles. **Plan 003 has been rewritten
   accordingly**: it no longer prescribes `as` assertions (which would have been
   an unnecessary loss of type safety) and instead instructs the executor to
   write the fix without them and add one only if the compiler actually demands
   it. Plan 001's Step 1 expectation was corrected too.
2. **A new P1 finding surfaced**: `@tiny-intl/preact` publishes a type entry
   point that re-exports `./useIntl`, a declaration file the build never emits →
   plan 006. Likely a downstream symptom of the very `exports` defect plan 005
   fixes (preact resolves with `moduleResolution: "bundler"`, which honours the
   broken `exports.types` path; react uses `"Node"`, which ignores `exports`
   entirely and reads the correct top-level `types` field). Plan 006's Step 1
   tests that hypothesis before changing anything and may conclude no-op.

## Bundle size — the constraint this project is judged on

Measured across the whole effort with an identical toolchain (esbuild `bundle+minify+esm+treeshake`,
framework externalised, then gzip -9 — a recipe that **reproduces the published
badge numbers exactly**):

| package | `794eb48` (before) | `49bd556` (plans 001–006) | delta |
|---|---|---|---|
| `@tiny-intl/core` | 1418 B | 1422 B | +4 B (gzip noise — minified size *fell*, 3116 → 3102 B) |
| `@tiny-intl/react` | **541 B** | 558 B | **+17 B** |
| `@tiny-intl/preact` | **727 B** | 741 B | **+14 B** |

The adapter regressions are the price of plan 003's correctness fix:
`typeof count === 'number'` costs far more bytes than `count`. Plan 007 recovers
them by switching to `!= null`, which is equally correct for these prop types
(all `T | undefined`), still true for `0`, and shorter after minification.

**Install size is a separate axis** and must not be conflated with the above.
Measured at `49bd556` via `npm pack --dry-run`: core 82.1 kB / 60 files,
react 19.0 kB / 8 files, preact 13.5 kB / 7 files. Of core's 82 kB, 16
sourcemaps are 35 kB and the published `src/` is 40 kB — see open question below.

**The residual +7 B / +8 B is not recoverable within the current design** and is
the honest price of the `count={0}` fix: `count != null` is shorter than
`typeof count === 'number'` but still longer than the original — buggy — bare
`if (count)`. Four such guards, gzipped, is about 7 bytes. Worth it.

If those bytes are ever needed back, the sanctioned lever is the **deprecated `d`
alias** (`packages/core/src/createTinyIntl.ts:56` and both adapters' `useIntl`),
already documented as "will be removed in next major". Deleting it in that major
frees bytes in all three packages at once.

**Guard against the next regression**: plan 007's `measure.mjs` harness (in that
plan's Step 1) could become a CI step that fails when a package exceeds a
committed byte budget. It would have caught plan 003's +17 B automatically.

### Open question for the maintainer

`@tiny-intl/core` publishes sourcemaps plus `src/` so consumer stack traces map

source-level debugging into the library. **This affects install size only — not
bundle size, and not the badges.** Deliberately left out of plan 007.

## Findings closed by plan 002 (removal, not repair)

Recorded with evidence in case the removal decision is ever revisited. These
were real, confirmed findings in `packages/solid-js`; the fixes below are what
plan 002 makes unnecessary.

1. **Every `useIntl()` primitive returned `[undefined]`** —
   `packages/solid-js/src/useIntl.tsx:22`. `memoizeCallback` called
   `fn.call(args)`, which passes the argument *array* as the `this` value and
   forwards **no arguments**. So `t('hello', { name: 'John' })()` — the exact
   call shape the package README documents — invoked `intl.t()` with zero
   arguments, `key` was `undefined`, and core's missing-key fallback
   (`packages/core/src/createTinyIntl.ts:116`) produced the literal string
   `'[undefined]'`. All eight primitives (`t`, `tc`, `n`, `dt`, `rt`, `sort`,
   `collator`, `list`) were affected identically. `<Translate>` was unaffected
   because it calls `intl.t` directly. **The fix would have been**
   `return fn(...args);` — one line, plus tests.
2. **`memoizeCallback` created a `createMemo` per invocation**, not per
   `useIntl()` call — harmless inside JSX (the surrounding reactive root owns
   it) but leaking an undisposed computation when called from an event handler
   or timer.
3. **`useIntl` returned `{ ...intl, ... }`**, which evaluates core's `locale`
   getter once, so the returned `locale` property was a frozen snapshot. The
   `getLocale` memo existed to work around exactly this.
4. **`<Translate count={0}>` / `number={0}`** — the same falsy-prop bug plan 003
   fixes in react and preact, at `packages/solid-js/src/Translate.tsx:66,78`.
5. **README examples were inconsistent with the accessor API** — `rt`, `list`,
   `sort` and `collator` examples omitted the trailing `()` that the
   implementation requires, and line 3 linked to a non-existent
   `./packages/solid`.

If Solid support is ever reinstated, note that the hard part was never the
adapter code — it was getting `vite-plugin-solid` to cooperate with vitest 0.34
in a test environment.

## Findings not planned (deferred, with evidence — do not re-audit)

Real findings, judged below the top five on leverage. Each is recorded with
enough evidence to plan later without re-running the audit.

1. **`change()` has a lost-update race, and silently drops `staticDict`**
   — `packages/core/src/createTinyIntl.ts:86-106`. `locale` is assigned before
   `await loadDict(locale)`, so two overlapping `change()` calls can leave
   `locale = 'en'` with the dictionary from `'de'`. Separately, the early return
   at line 87 means `change('de-DE', someNewDict)` while already on `de-DE`
   discards `someNewDict` entirely. And the runtime signature has a third
   parameter, `forceLoad`, that the public `TinyIntl['change']` type (line 48)
   does not declare, so callers cannot use it. Async `loadDict` via dynamic
   `import()` is the documented main path (`packages/core/README.md`), so this
   is reachable. Effort M, risk MED — needs a request-token or generation
   counter, which changes when subscribers fire.

2. **`mount()` is not re-entrancy-safe** — `packages/core/src/createTinyIntl.ts:226-230`.
   `mounted = true` is set synchronously before the `await`, so a second
   concurrent `mount()` resolves immediately while the first is still loading
   the dictionary. Both adapter READMEs tell users to call `mount()` inside an
   effect, and React 18 StrictMode double-invokes effects. The fix is to store
   the in-flight promise and return it. Effort S — worth folding into the same
   plan as finding 1.

3. **React and Preact `useIntl` return functions whose identity never changes**
   — `packages/react/src/useIntl.tsx:17-24` and the identical
   `packages/preact/src/useIntl.tsx:17-24`. `useCallback(intl.t, [changed])`
   always receives the *same* `intl.t` reference, so the returned identity is
   stable forever and the `changed` dependency accomplishes nothing. Values
   rendered directly are still correct (the component re-renders and `intl.t`
   reads the current dict from its closure), but a consumer writing
   `useMemo(() => t('key'), [t])` will never recompute on locale change. Effort
   S — wrap in a fresh arrow per `changed` value, or drop `useCallback` and
   document that the functions are not referentially stable.

4. **`t()` and `template()` treat an empty string as missing** —
   `packages/core/src/createTinyIntl.ts:111` and `:116`. `dict[key] || …` means a
   legitimate `""` translation falls through to the `.one` key and then renders
   `[key]`; `templateParams[key]?.toString() || …` means an empty-string
   template parameter renders `[name]`. Use `??` with an explicit `undefined`
   check. Effort S, risk LOW. Deliberately empty translations are a real
   localisation need (e.g. a suffix that exists in one language only).

5. **Dev-dependency advisories** — read from `package-lock.json`, **not**
   verified with `npm audit` (no `node_modules`, and installing would mutate the
   working tree). Versions carrying published advisories: `vite@4.5.2`,
   `esbuild@0.18.20`, `vitest@0.34.6`, `braces@3.0.2`, `micromatch@4.0.5`,
   `cross-spawn@7.0.3`, `tar@6.1.11`. **All are devDependencies**; the published
   packages have zero runtime dependencies, so consumer exposure is nil — this
   is a developer/CI-environment concern only. Remediation is a major-version
   sweep (vite 4→7, vitest 0.34→3, eslint 8→9, prettier 2→3, lerna 7→8),
   effort M-L, risk MED. Run `npm audit` first to get a real list. Explicitly
   out of scope for plan 001, which pins compatible testing libraries instead.
   Note plan 002 removes `eslint-plugin-solid` and its nested
   `@typescript-eslint/*` tree from the lockfile, shrinking this surface.

6. **`data?: undefined` typo in `TranslateProps`** — three of the four union
   members in each of `packages/react/src/Translate.tsx:24,34,45` and
   `packages/preact/src/Translate.tsx` declare `data?: undefined` where
   `date?: undefined` was clearly intended. The effect is that the "must not be
   set" constraint on `date` is missing from three branches. Fixing it changes
   which prop combinations typecheck for existing consumers — a breaking change,
   so it belongs with the discriminated union refactor noted in plan 003's
   Maintenance notes, in a major release.

7. **`Translate.tsx` is duplicated** — `packages/react/src/Translate.tsx` and

   keeps a `diff` check as a guard). It was triplicated before plan 002. A

8. **No `engines` field in any package** — CI currently claims to support Node

9. **`.vscode.tmpl/settings.json` is stale boilerplate from another project** —

10. **The documented `zero` plural key is unreachable in English and German** —
    surfaced by plan 003's executor, then verified directly:
    `new Intl.PluralRules('de-DE').select(0)` → `'other'`, and `'en-US'` → `'other'`.
    CLDR gives neither locale a `zero` category. But every README in the repo
    advertises `"supports also zero, two, few, many"`, `TinyIntlPluralDefinition`
    (`packages/core/src/createTinyIntl.ts:5-12`) exposes `zero?: string`, and the
    test fixtures all define `document.zero`. A user who writes
    `{ zero: 'No documents', one: '…', other: '{{count}} documents' }` and calls
    `tc('document', 0)` gets **"0 documents"**, never "No documents" — `tc` maps
    straight through `pluralRules.select(count)`
    (`packages/core/src/createTinyIntl.ts:120-127`) and never special-cases 0.
    The key is silently dead for the two locales the project's own examples use.
    Fix options: have `tc` prefer a `.zero` key when `count === 0` and one is
    defined, falling back to the CLDR category; or drop `zero` from the type and
    the docs. The first is a behaviour change, the second a breaking type
    change — needs a maintainer decision, hence no plan. Effort S either way.
    *(This is why plan 003's `count={0}` test asserts `'Dokumente'`: for de-DE
    the lookup resolves `document.other`, and the fixture happens to give `zero`
    and `other` the same string. The test still discriminates correctly —
    pre-fix it rendered the singular `'Dokument'`.)*

## Direction — options for the maintainer (not defects)

Presented separately because these are product calls, not bugs. Each is grounded
in something visible in this repo.

- **Typed dictionary keys.** `t(key: string)`
  (`packages/core/src/createTinyIntl.ts:49`) accepts any string; a typo is a
  runtime `[myTpyo]` in the UI. The dictionary shape is already fully described
  in the type system (`TinyIntlDict`, and `flattie` produces exactly the dotted
  keys `t` looks up), so a generic
  `createTinyIntl<Locales, const Dict>()` deriving a union of flattened keys is
  achievable **entirely in types — zero runtime bytes**, which is exactly this
  project's positioning. It is also the single feature most often cited for
  choosing typesafe-i18n or next-intl over a smaller library. Trade-off: deep
  recursive template-literal types can slow editor responsiveness on large
  dictionaries, and the `tc` key derivation (`${key}.${pluralKey}`) needs care.
  Coarse effort: M for a spike, L to ship well.

- **A server-side / per-request story.** `createTinyIntl` returns a closure with
  mutable module-level state (`locale`, `dict`), and every README example
  constructs it once at module scope. In an SSR server — Next.js, Remix, Astro —
  that single instance is shared across concurrent requests, so two users on
  different locales race over one `dict`. Nothing in the docs warns about this.
  The cheap version is documentation plus a per-request factory example; the
  fuller version is a provider that owns an instance and an explicit "create one
  per request" API. This is a common reason a modern i18n library gets ruled
  out. Coarse effort: S for docs, M for an API.

- **Whether to keep supporting multiple frameworks at all.** Dropping Solid
  (plan 002) takes the adapter count from three to two, and the two survivors
  are byte-identical copies of each other (deferred finding 7). That is a signal
  worth acting on deliberately in one direction or the other: either invest in a
  shared framework-agnostic layer so adding an adapter is genuinely cheap
  (making Vue/Svelte/vanilla plausible), or narrow to react + preact as the
  supported surface and say so in the README. The current middle position —
  hand-maintained copies, no tests — is what produced the Solid situation.
  Coarse effort: M either way; the decision matters more than the code.

- **A dictionary-consistency check.** Nothing verifies that `de-DE.json` has the
  same key set as `en-US.json`, or that every plural entry has the `one`/`other`
  its locale requires — a missing key surfaces as `[key]` in production. A small
  build-time checker (or a `flattie`-based test helper shipped from
  `@tiny-intl/core/utils`) would catch it. This is the "friction users work
  around by hand" case. Coarse effort: M; note it is a new product surface (a
  CLI or a build plugin), not just a function.

## Findings considered and rejected

So nobody re-audits them:

- **Prototype pollution in `flattie`** (`packages/core/src/utils/flattie.ts:28`,
  unguarded `for…in`): not exploitable here. Dictionaries are developer-authored
  assets, not user input, and a nested `__proto__` becomes an ordinary flat
  string key like `"__proto__.foo"` rather than a prototype write. A top-level
  `__proto__` holding a primitive is a silent no-op. Not worth a guard.
- **`collator()` returning `formatter.compare` unbound**
  (`packages/core/src/createTinyIntl.ts:181`): safe. `Intl.Collator.prototype.compare`
  is specified as a bound accessor, so it does not need `this`.
- **Version drift between packages** (core and solid-js at `1.2.0`, react and
  preact at `1.2.1`, `lerna.json` at `1.2.1`): normal lerna fixed-mode
  behaviour — only packages with changes get republished. Not a bug.
- **`files: ["lib", "src"]` in `packages/core/package.json` shipping source**:
  deliberate. tsup runs with `sourcemap: true` and the emitted `.js.map` files
  reference `../../src/*.ts`, so `src` is what makes consumer source maps
  resolve. Documented in plan 005 so nobody "optimises" it away.
- **The duplicated `numberFormatCache.clear()`**
  (`packages/core/src/createTinyIntl.ts:92` and `:95`): real but harmless — all
  five caches are cleared, one of them twice. Folded into plan 004 rather than
  tracked separately.
- **`console.warn` on every unsupported-`Intl` call** in `rt`, `collator` and
  `list`: noisy in old browsers, but the existing test at
  `packages/core/tests/index.test.ts:176-208` exercises these paths and the
  warning is arguably the point. Not worth changing.
- **The adapter packages' `dist/stats.html` output**: `rollup-plugin-visualizer`
  writes to a directory those packages do not publish. Harmless — unlike core,
  whose entire vite build was dead (plan 005).

## What was not audited

- **Runtime behaviour.** Nothing was executed: no `node_modules` was present,
  and installing would have mutated the working tree. Every finding comes from
  reading source, configs and the lockfile. Plan 001 Step 1 is the first
  execution of anything.
- **`npm audit`.** Deferred finding 5 lists versions read from
  `package-lock.json` against known advisories; it is not an audit report.
- **Built output** under `packages/*/lib` and `packages/*/dist` was inspected
  only for *which files exist* (evidence for plan 005). Its contents were not
  reviewed — the sources are.
- **The published npm tarballs.** Plan 005's diagnosis is based on the local
  build; `@arethetypeswrong/cli --pack` in that plan is the check against what
  consumers actually receive. Plan 002 Step 1 records the published
  `@tiny-intl/solid-js` versions for the deprecation handoff.
